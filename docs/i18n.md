## Internationalization (i18n) setup

This project uses [`next-intl`](https://next-intl.dev) v4 together with the Next.js App Router. Locales are encoded in the URL as a leading
segment, e.g. `/pl`, `/en/about`, `/de/contact`.

### Supported locales and routing

- Locales are defined in `i18n/routing.ts`:
  - `locales`: `["en", "de", "pl"]`
  - `defaultLocale`: `"pl"`
- The App Router uses a dynamic `[locale]` segment under `app/[locale]`:
  - Example routes: `/pl`, `/en`, `/de`, `/pl/some-page`, etc.
- `hasLocale` from `next-intl` is used in `app/[locale]/layout.tsx` to validate that `params.locale` is one of the configured locales. Invalid
  locales trigger `notFound()`.

### Middleware and locale negotiation

- `proxy.ts` configures `next-intl`’s middleware:
  - `createMiddleware(routing)` uses the same `routing` config as the app.
  - The `matcher` excludes API routes, Next.js internals (`/_next`, `/_vercel`) and asset-like paths (those containing a dot).
- The middleware is responsible for:
  - Matching locale prefixes in URLs.
  - Redirecting or rewriting to include a locale where appropriate.

### Request configuration (`i18n/request.ts`)

- `i18n/request.ts` exports a default `getRequestConfig` from `next-intl/server`.
- It currently:
  - Reads `requestLocale` (typically matching the `[locale]` URL segment).
  - Verifies it via `hasLocale(routing.locales, requested)`.
  - Falls back to `routing.defaultLocale` when the requested locale is not supported.
  - Returns an object with a `locale` property.
  - Dynamically imports the correct JSON file from `messages/<locale>.json` and exposes it as `messages`.
- According to the official docs, this file is also the recommended place to provide **messages** (translations) for the current request, which is
  now implemented in this project.

### Messages (translation files)

- Message files live in the top-level `messages` directory:
  - `messages/en.json`
  - `messages/de.json`
  - `messages/pl.json`
- All three files currently expose the same structure:
  - Root namespace `HomePage` with a `title` key, e.g.:
    - `messages/en.json`: `"HomePage.title" = "Hello world!"`
    - `messages/de.json`: `"HomePage.title" = "Hallo Welt!"`
    - `messages/pl.json`: `"HomePage.title" = "Witaj Świecie!"`
- These files are designed to be loaded based on the active locale so that components can call `useTranslations('HomePage')` and then
  `t('title')`.

### Provider and usage in components

- `app/[locale]/layout.tsx`:
  - Wraps the page content in `<NextIntlClientProvider>{children}</NextIntlClientProvider>`.
  - Because no explicit `messages` prop is passed, next-intl expects `locale` and `messages` to come from the request configuration in `i18n/
request.ts`.
  - The layout also checks `params.locale` against `routing.locales` to guard against unsupported locales.
- `app/[locale]/page.tsx`:
  - Uses `useTranslations('HomePage')` from `next-intl`.
  - Renders `t('title')`, which expects the key `HomePage.title` to be present in the messages for the current locale.

### Current behavior

- `i18n/request.ts` now returns both `locale` and the corresponding `messages` object for each request by importing `messages/<locale>.json`.
- `NextIntlClientProvider` in `app/[locale]/layout.tsx` picks up this runtime configuration, so calls like `useTranslations('HomePage')` resolve
  to the strings defined in `messages/*.json` without missing-message errors.
- To add new translations, update the appropriate JSON file in `messages/` and reference the keys via `useTranslations` in your components.
